# Панель проверки отчётов биржи заданий

Панель для продвижения товаров маркетплейсов (Wildberries, Ozon) через биржу микрозаданий UNU: менеджер ставит ТЗ, панель создаёт задания, следит за выполнением и **сама проверяет 2–3 тысячи отчётов исполнителей в день** — правила, ИИ-агент и человек только на спорных.

Сделано за 2 дня как тестовое задание, один, с Claude Code: я ставил задачи и проверял, агенты писали код. Код прошёл ревью Codex, Gemini, Claude Sonnet и Haiku и аудит безопасности [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill).

**Демо без установки:** https://zgxd.ru/test/unu-panel/ — копия на сгенерированных данных (2 400 отчётов в сутки).

## Что решает

Ручная проверка: менеджер открывает каждый отчёт, сверяет 3–4 скриншота и контрольный ответ. На 2 000+ отчётов в день это несколько человек. Панель снимает с человека почти всю рутину:

| | Результат на демо (2 998 отчётов за сутки) |
|---|---|
| Решено без человека | **88%** |
| Честные отчёты, забракованные автоматически | **0** из 2 690 |
| Подделки на контрольной пачке, пойманные ИИ-агентом | **12 из 12** |
| Токены на картинки | примерно **в 6 раз меньше**: 12 скринов на одном листе |

## Стек

Python (FastAPI, SQLite, Pillow), интерфейс на чистом JavaScript + Chart.js, проверка скриншотов моделью Claude (Vision) или субагентом Claude Code. Около 4 400 строк Python и 570 строк JS. Работает локально или на обычном хостинге через CGI (`tools/hosted/`).

## Как это устроено

- **Товары и ТЗ.** Товар → поисковые запросы → место в выдаче, график за 14 дней, выполнено против плана. «Новое ТЗ» считает объём и бюджет и создаёт задания в UNU по API.
- **Очередь проверки.** Спорные отчёты сверху, скрины крупно, при «похожем скрине» рядом оригинал, горячие клавиши.
- **Исполнители.** Тревоги: «один делает всё», фермы на одном IP, страна по IP, чёрный список.
- **Журнал.** Всё, что панель отправила на биржу, и все изменения правил.
- **Площадки подключаются отдельно** (`app/platforms/`): UNU и демо-генератор; новая биржа — один класс.

## Как сделано, чтобы не смотреть все картинки

| Шаг | Что смотрит | Демо: 2 400 новых в сутки, ~3 000 проверено за первые сутки |
|---|---|---|
| 1. Правила | Текст и отпечатки файлов, без просмотра картинок: контрольный ответ, копии скринов, IP, скорость | решают 89% |
| 2. Агент | Первые 3 отчёта каждого нового исполнителя; 3% случайных принятых; отчёты, где не хватает только картинки (нет контрольного вопроса, скрин не скачался) | ~8% потока (240 из 3 000 в демо, 20 листов) |
| 3. Человек | Копии скринов, фермы, «слишком быстро», «много у одного», плохая история, «агент не уверен» | ~10% |

- **Листы вместо картинок.** Агенту уходят листы 4×3: 12 скриншотов на одном изображении с номерами + `tasks.json` с товаром, правильным ответом и текстом исполнителя по каждому номеру. Одна картинка вместо двенадцати — примерно в 6 раз меньше токенов на изображения.
- **Агенту — только то, что картинка решает.** Хороший скрин снимает сомнение, только если оно про картинку: у задания нет контрольного вопроса или скрин не скачался. Скорость, одинаковый текст, «много у одного», копию чужого скрина, ферму на IP и плохую историю картинка не опровергает — такие отчёты идут человеку (`learning.agent_resolvable()`; список расширяется только через обучение и только «картиночными» причинами).
- **Агент видит все скрины отчёта:** 2–4 скрина этапов ложатся на плитку сеткой 2×2 с номерами.
- **Доверие зарабатывается.** Первые 3 отчёта каждого исполнителя агент смотрит всегда, потом — только выборочно. Доверие считается по реально проверенным агентом отчётам, а не по отправленным в пачку. В режиме «авто» оплата новичку не уходит, пока агент не ответил. Так ловятся исполнители, которые списывают контрольный ответ из чата, а прикладывают скрин не того товара: правила этого не видят.
- **Ответ агента проверяется строго.** `verdicts.json` с неизвестным номером или вердиктом не принимается целиком; пропущенные номера возвращаются в очередь; ответ на отчёт, который исполнитель успел пересдать после доработки, отбрасывается.
- **Агент — любой.** Обмен через папку `data/agent/batch-*`: панель кладёт листы и `tasks.json`, агент пишет `verdicts.json`, панель забирает сама. Готовый субагент Claude Code — `.claude/agents/proverka-skrinov.md` (в Claude Code: «проверь пачку batch-…»). Тот же формат можно отдать Codex или вызвать API по расписанию.

**Проверено 23.11 на демо** (субагент Claude Sonnet, 72 отчёта на 6 листах):
- контрольная пачка `tests/agent_testset.py` — 12 подделок (скрин не того товара или без действия, контрольный ответ при этом верный) вперемешку с 12 честными: агент поймал **12 из 12**, честных не забраковал;
- обычная пачка из 48: все честные приняты; один украденный скрин агент по картинке не отличил — он и не должен: такой отчёт по правилу остаётся человеку;
- без агента правила пропускают эти подделки в оплату (в демо ~10% брака) — именно эту дыру агент и закрывает;
- одна пачка из 12–24 скринов — ~15 секунд и 80–90 тыс. токенов субагента.

## Обучение проверки: решения человека делают ИИ самостоятельнее

Спорные отчёты не просто уходят человеку — его решения учат проверку (`app/learning.py`, вкладка «Проверка → Обучение»).

1. **Лог разбора.** Каждое решение человека пишется в таблицу `reviews` снимком: причины с исходными весами, ответ агента, решение, комментарий, текст и файлы отчёта на тот момент.
2. **Агент «в тени».** До 10% каждой пачки — спорные отчёты, которые агенту пока не доверены. Решает всё равно человек, а ответ агента только сравнивается с его решением.
3. **Предложения.** По каждой причине сомнения панель считает, как часто человек с ней соглашался:
   - человек почти всегда принимает (90%+) → снизить вес (до 40% исходного, не до нуля);
   - когда причина единственная, человек почти всегда бракует → сразу «вернуть на доработку» (не «отклонить» — безвозвратно только доказанное);
   - агент совпал с человеком в 95%+ и поймал 90%+ брака → отдавать причину агенту. Только «картиночные» причины: скорость, ферму на IP, историю и копию скрина снимок не опровергает.
4. **Защита от самообмана** (по ревью Codex и Sonnet 24.11):
   - выводы — по старым 70% решений, проверка — на свежих 30%, которых подбор не видел;
   - не больше 2 решений одного исполнителя на причину и минимум 10 разных исполнителей: ферма не «научит» проверку;
   - предложение показывается, только если на свежих решениях **ни один брак не ушёл бы в оплату** и лишних отказов честным не больше 5%; ошибки не взаимозачитываются;
   - веса считаются от исходных, поэтому одно и то же не снижается повторно.
5. **Применяет человек кнопкой.** Сама проверка правила не меняет: исполнители подстраиваются, и самообучение можно было бы приучить пропускать брак. Любая поправка откатывается, всё пишется в журнал; после поправки перепроверяются только отчёты с этой причиной.
6. **Ошибки агента — в его примеры.** Случаи, где агент разошёлся с человеком, кладутся в каждую пачку (`examples.json`), агент читает их перед проверкой.

**Демо** (`DEMO=1 python tools/demo_learning.py --reviews=260`): «человек» разбирает 260 отчётов по правде генератора, агент в тени видит половину. Итог 24.11 на чистой базе: агент совпал с человеком в 116 из 125; панель предлагает одно — «Слишком быстро»: вес 20 → 8 (человек принял 44 из 44 у 28 исполнителей; на 78 свежих решениях ещё 39 отчётов без человека, брака в оплату 0). Очередь человеку — 70 → 39. «Одинаковый текст» агенту не отдаётся: брака в выборке было 2 — нельзя проверить, что агент его ловит.


## Запуск за 2 минуты

```bash
pip install -r requirements.txt
python run.py --demo     # демо-данные
python run.py            # живой аккаунт: нужен файл .env с UNU_API_KEY=...
```

Откройте http://127.0.0.1:8800. Без ключа запускается демо: около 2 400 отчётов в сутки, 7 дней истории, первая синхронизация занимает около 2 минут (16 800 отчётов, ~3 000 из них проверяются). За один цикл проверяется до 5 000 новых ожидающих отчётов; остальные будут проверены в следующих циклах. Демо генерирует новые отчёты и после запуска.

Для UNU создайте рядом с `run.py` файл `.env`:

```dotenv
UNU_API_KEY=ваш_ключ
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `UNU_API_KEY` | пусто | Ключ API UNU. |
| `UNU_API_URL` | `https://unu.im/api` | Адрес API UNU. |
| `DEMO` | `1` без ключа, иначе `0` | `1` включает демо-площадку. |
| `DB_PATH` | `data/demo.sqlite` в демо, иначе `data/panel.sqlite` | Путь к SQLite. Рядом хранится кеш файлов. |
| `SYNC_INTERVAL_SEC` | `300` | Интервал цикла в секундах; в демо цикл запускается каждые 60 секунд. |
| `DECISION_MODE` | `advise` | Начальный режим решений; настройку можно изменить в панели. |
| `AUTO_APPROVE_SCORE` | `80` | Минимальный балл для рекомендации принять при отсутствии hard-находок. |
| `NEAR_DUP_HAMMING` | `12` | Максимальное расстояние Хэмминга для похожих скриншотов. |
| `WORKER_DAY_SHARE` | `0.01` | Доля отчётов проекта за сутки для порога концентрации. |
| `WORKER_DAY_MAX` | `5` | Нижняя граница порога концентрации. |
| `WORKER_TASKS_DAY` | `4` | Сколько разных заданий кабинета один исполнитель может пройти за сутки без пометки. |
| `GEO_HOME` | `RU,BY,KZ` | Страны, откуда ждём исполнителей. Нужна таблица `data/ipcountry.csv` (`python tools/geo_update.py`). |
| `GEO_WEIGHT` | `5` | Вес правила «IP не из этих стран». |
| `BLIND_TO_AGENT` | `1` | Отчёты заданий без контрольного ответа не оплачиваются без проверки скринов агентом или человеком. |
| `READ_ONLY` | `0` | `1` — на площадку ничего не отправляется: только синхронизация и проверка. |
| `HOSTED` | `0` | `1` — запуск через CGI без фоновых потоков (`tools/hosted/`). |
| `PANEL_HOSTS` | пусто | Имена хоста, с которых панель принимает запросы, кроме локальных (для сайта). |
| `AGENT_TILE` | пусто | Размер плитки отчёта на листе агента, например `1500x1400` вместе с `AGENT_SHEET_COLS=1`, `AGENT_SHEET_ROWS=1` — для крупных скринов с ПК. |
| `ANTHROPIC_API_KEY` | пусто | Ключ для проверки скриншотов Claude. |
| `VISION_MODEL` | `claude-opus-5-5` | Имя модели Claude. |
| `VISION_ENABLED` | `1` | Проверка включена только при значении `1` и наличии ключа. Дополнительно нужен пакет `anthropic`. |

`run.py` также принимает `HOST` (по умолчанию `127.0.0.1`) и `PORT` (по умолчанию `8800`).


## Тесты

```bash
python tests/eval_demo.py        # точность правил и агента на демо-разметке
python tests/test_new_rules.py   # правила этапов и ссылок
python tests/agent_testset.py    # контрольная пачка: известные подделки + честные
```

Честно об ограничениях: точность измерена на сгенерированных данных и контрольной пачке; на реальном потоке пороги надо подстроить по первой неделе ручной разметки. Один процесс без очередей — на годовом объёме нужен Postgres.
